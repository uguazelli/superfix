# SuperFix field repairs implementation plan for Luna

Build four capabilities into the existing technician workspace. The first delivery should let a technician open a “refrigerator is warm” case, identify the exact model, enter separate fridge and freezer readings, and see which evidence and manual page support the next check. By the final delivery, a colleague should be able to take over the return visit, work through a connection loss, and find the repair again by serial number or job reference.

## Delivery order

| Increment | Deliverable | Dependency |
| --- | --- | --- |
| 1 | Appliance identification and a job reference on every case | Existing intake and photo upload |
| 2 | Reviewed warm-refrigerator workflow and pilot outcome report | Increment 1. Real guidance needs a selected family, service manual and technician reviewer |
| 3 | Return visits, waiting parts, callbacks and a Due back list | Increment 1. Can ship while the refrigerator procedure is under review |
| 4 | Search, appliance history and assignment to another technician | Increment 1 for search and identity, increment 3 for visit history |
| 5 | Mobile autosave, offline drafts and reliable synchronization | Draft storage can start after increment 1. Finish replay tests against visit and assignment changes |

Deliver each increment through the UI, API and persistence layer. Use the current React and TypeScript features, TanStack Query, Zustand, English translation resources and shared Tailwind/shadcn components. Extend the Spring Boot `repair` domain, PostgreSQL migrations and existing Docker Compose services. The approved scope leaves RAG, estimates, service orders, invoicing, customer approvals and online payments for later.

## 1. Identify the appliance and the job

- Add a stable, human-readable job reference, generated by PostgreSQL and unique within the company. Backfill existing cases once and keep UUIDs as API identifiers. Show the reference on the list and case header.
- Extend intake with an optional serial number and explicit model confirmation. On a phone, let the technician take or attach a model-plate photo, read it at full size, and type or correct the model. Manual entry must also work without a photo. Mark photos as plate or symptom and count both toward the existing four-photo limit. Treat existing photos as symptom photos.
- Create company-owned appliance records for confirmed units. Reuse a record on an exact company, category, brand, model and serial match. Keep the entered values, preserve meaningful suffixes and leading zeros, and enforce uniqueness for the normalized match under concurrent creation. A case with a missing serial stays searchable by job reference.
- Add a nullable appliance link with a tenant-aware foreign key on `repair_cases`. Retain each case's intake snapshot. Let a company admin link a historical case after confirming the unit while preserving its recorded intake and closure. In the OpenAI adapter, explicitly select diagnostic fields and symptom photos. Exclude plate attachments and the serial and job reference fields from provider requests.

**Acceptance tests**

Two visits for the same confirmed unit in one company link to one appliance. Two units of the same model with different serials stay distinct. Two companies can enter identical plates independently. Upgrade a database containing an open case, a closed case and photos, then open each through the original URL.

## 2. Pilot one model-specific refrigerator workflow

1. Use Whirlpool side-by-side refrigerator family `WRS321SDHV` as the concrete example. The current candidate covers exact model strings `WRS321SDHV`, `WRS321SDHV00`, `WRS321SDHV01` and `WRS321SDHV02`. Its source is Whirlpool service manual `W11296289` (©2018), pages 1-11, 2-2–2-5 and 3-3. The candidate records no serial-number cutoff; confirm the exact unit against its product Tech Sheet and do not apply it to another model suffix. The user identified themselves as reviewer; the procedure remains unreviewed until they approve the actual questions, branches and safety notes. Do not enable it for field use before that review.
2. Add a versioned procedure under backend resources keyed by category, complaint and model family. Record the covered aliases, any serial or hardware revision required to distinguish variants, question and cause IDs, branches, units, evidence prerequisites, and source page for each check. Validate references and reachable outcomes at build time. Record the reviewer and review date. Pin the procedure revision when diagnosis starts and retain the displayed questions, findings and citations in case and attempt history.
3. In intake, let the technician select **Refrigerator is warm**. In the existing rounds UI, ask for separately identified fresh-food and freezer temperatures. Show the unit and allow the existing unknown, unavailable and not-performed answers. Use the reviewed branches to choose subsequent checks. A finding must show the observations that support it, the applicable guidance, and a usable manual link with document revision and page.
4. Extend `DiagnosticAi` so both providers use the same eligible checks and evidence rules. The server validates model applicability, branch conditions and cited answers. Apply existing hazard escalation before selecting a procedure. For an unsupported model, offer the generic workflow with a clear coverage message. For insufficient evidence, request an eligible check or finish inconclusively. Preserve queue idempotency, quotas and the fresh-evidence rule after a failed verification.
5. Capture an optional structured confirmed cause in the work log alongside the existing free text. Provide a company-admin pilot report by procedure revision. For closed cases with both codes, compare the first suggested cause to the final technician-confirmed cause. For cases with a performed first verification, report how many passed that test. Show counts and denominators, list unknowns and inconclusive cases separately, and exclude demo cases. Keep AI helpfulness as a separate measure.

**Acceptance tests**

Fixture cases with RC and FC service-mode results exercise the matching sensor-circuit branches and the inconclusive fallback. Test an unsupported model suffix, unavailable readings, a hazard, an invalid provider selection and a failed-test follow-up. Publish a second guide revision and confirm an older case still shows its original citations. Verify report counts on known outcomes. The real pilot starts once the reviewer has checked the branches and manual links for the chosen family.

## 3. Manage return visits, waiting parts and callbacks

- Add **Schedule return** to an eligible open case. Capture the reason, return date, next action and any needed parts with name, optional part number and quantity. Track requested, received or cancelled parts separately from the work log of parts actually used.
- Store return visits as company-scoped rows with scheduling and actual visit dates, actor and notes. Allow one scheduled return per case. Scheduling pauses the case and preserves its prior stage, including when it was already paused. Rescheduling changes the date. Starting the visit resumes the saved stage. Cancelling leaves the case paused and removes the visit from the due list. Make the existing **Resume** action reconcile a scheduled return in the same transaction. Record each change for the timeline.
- Add a paginated **Due back** view with overdue, today and upcoming returns. Store the promised day as a calendar date. Use the technician-selected local day for grouping and filter through the same ownership rules as the case list.
- From a closed repair, **Create callback** opens a new draft linked to the original case and appliance. Give it its own job reference, current symptoms and hazard assessment, diagnostic rounds, verification and checklist. Keep the original closure and feedback intact. A failed verification on an open case continues to use **Continue diagnosis**.
- Extend the API under `/api/v1` with `POST /cases/{id}/returns`, `PATCH /cases/{id}/returns/{returnId}` and `POST /cases/{id}/callbacks`. Scope links by company. Use the case version for edits and a stable client operation ID for creates. Under concurrent retries, the same authorized request must return the same visit or callback.

**Acceptance tests**

Schedule a return from the checklist, reschedule it, mark the part received, and resume at the checklist with the original readings. Verify the due list across a day boundary and after cancellation. Double-submit a callback and get one new draft. The original closed case still shows its original test, tool check and feedback.

## 4. Find past work and hand it to a colleague

- Extend the existing paginated case list with job reference and exact serial search alongside category and status. Index company plus reference and company plus normalized appliance identifiers. Apply visibility filters before computing result counts. Include assignment, next visit date and the job reference in each row.
- Add a case-scoped appliance history view. Show dated visits, confirmed faults, parts used, readings, verification outcomes and linked callbacks for cases the viewer can access. Cases without an identified unit still show their own visit history. Company administrators can browse the full history within their company.
- Use the existing `technician_id` as current assignee and preserve the creator separately, backfilled from the original owner. Give company administrators a **Hand off** action for an open case with an active same-company technician and a next-action note. Record old and new assignees, actor and time. Show the incoming technician the last attempt, pending parts and next action together.
- Implement `PUT /cases/{id}/assignee` with a case version, and `GET /cases/{id}/history` through the repair authorization service. After reassignment, check current ownership for lists, details, writes and photos. A callback handoff can carry a technician-written summary. Opening its parent still requires access to the parent case.

**Acceptance tests**

As a company administrator, find a unit by serial and hand its return visit from technician A to B. B can read the previous visit and measurements in the assigned case. A loses server access to that case and its photos. A technician from another company gets no case, search count or history entry for it. Reject inactive assignees and competing stale assignments.

## 5. Preserve mobile drafts through a connection loss

- Autosave an unfinished intake, round answers, work log including readings, checklist edits and pending intake photos. Store drafts and photo blobs in IndexedDB under the last verified company, user, local case ID and applicable attempt or round. Keep partial input locally even when a field is still invalid for a server save. Display **Saved on this device**, **Syncing**, **Synced**, or **Needs attention** according to the last successful write.
- Let a technician enable offline access on a trusted device. Cache the application shell and static assets with a service worker so a previously opened repair can reload offline. Store only the fields needed for that draft. Keep authenticated API responses and photo URLs out of the shared asset cache. Use a server-issued expiry from the most recent `/auth/me` check to bound offline access. After expiry, lock drafts until the same user signs in. At explicit sign-out, warn about unsynced work and clear that user's device data when they proceed.
- On reconnect, verify the user, obtain fresh CSRF tokens, and sync valid changes in order per case. Create a local-only intake on the server first, then upload pending photos. Add stable client IDs and database uniqueness to case creation and photo uploads. A retry after a lost response must recover the original case or photo without using another slot. Preserve existing upload formats, limits and draft-stage checks.
- Use the acknowledged case version for each write. On conflict, preserve the local draft, fetch the current editable round or section, and show both versions for review. Stop replay if the case has moved to another attempt or closed. If access was revoked, remove the case and its pending writes from that device after the server confirms the denial. Explicit actions such as submitting to AI, scheduling a return, handing off and closing require a connection and synchronized edits.
- Test the installed shell on a phone over HTTPS. Handle device storage exhaustion before claiming that a draft or image is saved. Provide a retry and keep already saved edits recoverable. [Service Worker specification](https://www.w3.org/TR/service-workers/) · [WebKit storage behavior](https://webkit.org/blog/14403/updates-to-storage-policy/)

**Acceptance tests**

Put a phone offline, enter readings, close and reopen the app, reconnect and recover the same values on a second device. Repeat with a new intake and two photos, dropping the response after the server accepts one upload. Expect one case and two photos. Cover a full device store, an expired session, a different user signing in, a competing edit and a reassignment during disconnection. Reconnecting alone must generate zero AI requests and zero case closures.

Exercise every copy/update of `RepairData.Detail` against the new fields.
- Run `mvn verify` in the backend, `npm ci && npm run build` in the frontend, and the [Compose smoke suite](../scripts/smoke.py) against isolated database and photo volumes in mock mode. Exercise the generic workflow for all five appliance categories, including the existing escalation rules. Add mobile browser tests for offline reload, retry and account switching. Test a fresh install and an upgrade with pre-existing data. Rehearse recovery using matching database and photo backups. A live-provider check can use synthetic evidence once the operator supplies an API key.

### Final walkthrough

Technician A identifies a pilot refrigerator and records both temperatures. The proposed finding cites the applicable manual page. A schedules a return for a part. A company admin finds the job by reference and assigns B. B resumes the visit, records a reading offline, syncs it, verifies the repair and completes the tools checklist. A later callback appears under the same serial with its own job reference. Check the original outcome, pilot counts and access from a second company.

## Implementation status

The project now contains the API, persistence, and UI workflows for job/appliance identity, return visits and parts, callbacks, search/history, technician handoff, offline drafts and synchronization, a company-scoped pilot outcomes report, and archiving/restoring/deleting closed repair history. Permanent deletion is company-admin-only, removes related case data and photos, and is blocked while callback cases reference the repair. Return ordering follows the technician's local calendar day, and offline sessions require explicit per-device opt-in and use the server-issued expiry. Migrations V2 through V5 add the related schema and indexes. English strings remain in the i18n resource so more locales can be added later.

The refrigerator training fixture remains synthetic. A separate, source-backed Whirlpool WRS321SDHV candidate is implemented with exact model aliases, an intake round, the manual's RC/FC sensor result checks, explicit circuit-only branches, an inconclusive fallback, and a pinned manual citation. It is marked unreviewed and can only run in demo mode. The guide does not identify a failed part or instruct a replacement; the exact unit's Tech Sheet remains necessary. The user has identified themselves as reviewer, but approval is pending. Production selection and the outcomes report remain gated until review metadata is recorded.

The implementation has not been run through the verification steps above in this turn. Complete the migration-upgrade, Compose, backend, frontend, and offline-device checks before using it with technicians.
